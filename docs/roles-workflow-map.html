Precedent already exists in your own repo: assistant-context.md's header explains this exact failure mode for the in-app assistant. You are applying a rule you already wrote — to the agents instead of the product.

Why this is the biggest token win available

  • status.md is 52 KB ≈ 13K tokens. Every agent, every session.
  • It contains three conflicting "current state" headers and ~15 internal contradictions.
  • So agents pay the full cost and can still come away wrong — the worst combination.
  • A one-screen current-state file costs roughly 600 tokens and is unambiguous.
No model downgrade available to you saves as much as this, and unlike a downgrade it makes output better rather than cheaper-but-worse.

What this changes in practice

↓
Before
Design writes a 38K-char spec → Frontend reads it and re-implements everything from scratch → drift is discovered later by screenshot. Both sides build the button.
↑
After
Frontend pushes the real component library up once. Design edits real components. Frontend pulls. The spec shrinks to what a spec is actually good at — screen composition, states, formulas, acceptance criteria — instead of re-describing a button in prose.
Realistic saving: the spec stops being 38K characters. That directly attacks the failure you already hit — the port that ran to a 97% usage stop and still self-reported wrongly. A shorter spec is a spec that gets followed.

What still needs a human in the loop

  • Screenshot verification survives all of this. Component sync proves a button matches. It cannot prove a screen exists. The Opponents tab was missing entirely while every test passed — sync would not have caught that either.
  • Design has no read access to docs/. If a backend field is renamed, Design will not know. Under Principle #1 a field rename is a product change, so it must be told explicitly.
  • The 24-config matrix and null-states are invisible to Design. It cannot see which values are honestly null in nulls.json, so it will keep designing populated states unless told which cells are empty and why.
First sync should be a one-component pilot — push a single button or chip, confirm the round trip, then scale. Do not push the whole library on the first attempt.

The sprint loop — one cycle, 1–2 coding sessions

Sprint exit condition, unchanged and non-negotiable: the app still runs. A half-built feature degrades to an explicit "not computed" state — never a crash, never a half-rendered screen.

## Agent operating rules

Reading order at session start:
1. docs/CURRENT-STATE.md  — canonical state. Trust this.
2. docs/operating-model.md — your role, effort, gates.
3. Only the specific ADR or doc your task names.

Do NOT read docs/status.md for current state. It is an
append-only historical log containing superseded figures.
Same hazard as decisions.md, described in
docs/assistant-context.md's header.

Write-back, end of every session:
- Update docs/CURRENT-STATE.md IN PLACE. Replace stale
  lines; do not append a new section.
- Append the session narrative to docs/status.md.
- New decision -> ADR in docs/decisions.md.
- Contract schema change -> bump version AND note that
  the frontend must be told.

Completion reporting:
- Report commit hash + test count. Not prose summaries.
- UI/visual work is NEVER "done" on your own report.
  State it as "built, pending screenshot verification."

Standing brief to paste into Claude Design

You produce the design system and screen specs for a
fantasy football draft assistant. You cannot see the
code repo — assume nothing about current build state.

Four hard constraints, not style preferences:
1. Every number on screen traces to a named backend
   field. No decorative numbers.
2. An explicit null is a real state. "0%", "0", "—" and
   "not computed" are four different claims. Never
   substitute one for another.
3. Never show a part-applied recompute. Mid-recompute,
   everything holds its pre-edit value.
4. Density IS the product. Do not add whitespace or
   raise font sizes to modernise. ESPN's 2025 redesign
   is the cautionary tale.

Typography: two roles only. IBM Plex Sans for names,
prose, labels, nav. IBM Plex Mono for numeric cells
only, tabular-nums scoped to the cell. Position and
team codes (WR1, LV) are LABELS — sans, not mono.

Radius: 4-6px chrome, 0 on data cells and table rows,
10-12px modals only. No gradients or shadows except a
side-panel drop shadow. Colour never carries meaning
alone — every colour signal needs a redundant non-
colour cue.

Deliverables: components go through /design-sync (the
frontend engineer runs it). Screens still need a written
spec — keep it tight and structured, not 38K characters
of prose.

On marketing skills — deliberately not used yet

You asked me to use everything loaded. I used process documentation, dashboard building, design handoff, and roadmap prioritisation, because each maps to a decision on the table today. I did not run the marketing skills, and I'd rather say why than produce filler: this is a private-use product with no launch date, no pricing, no audience, and unresolved licensing (the nflverse headshots are personal-use-only until revisited). Positioning work now would be written against a product whose signature claim — calibrated availability — is not yet calibrated, because you have 1 of the ~30 mocks needed to validate it. The right trigger for the marketing skills is after the real-world validation loop produces evidence the rank beats consensus. At that point marketing:competitive-brief and marketing:campaign-plan have something true to work with. Right now they'd generate claims you'd have to walk back.
