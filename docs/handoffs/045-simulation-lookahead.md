recommendation. Founder: *"Roster awareness should be based on simulations if possible, available
players, see into the future if possible."*

This is P3-1 (VONA), P3-3 (pick-gap urgency) and P3-4 (draft simulation as the evaluation metric)
converging. All three are already in `deferred.md`; this is the request that makes them worth doing
now.

## What it means concretely

Today the recommendation answers *"who has the most value over replacement right now."* The founder is
asking it to answer *"which pick leaves me with the better roster two picks from now."*

Mechanically: from the current board state, simulate forward to the user's next pick under the
opponent model, for each candidate choice. Compare not the immediate VBD but the **expected value of
the roster you end up holding**. That is VONA — value over the next available alternative — and the
schema prerequisite is already satisfied: `rankings` stores `spread_sd`, `rank_best`, `rank_worst` per
source per `as_of_date` (P3-1, marked satisfied 2026-07-25). Only the algorithm is missing.

## The objection to address head-on — and why it is weaker here than elsewhere

Simulated drafts are generated by **our own opponent model**, whose `lambda = 0.352` was fitted on a
single real draft with 10 clusters. Any claim resting on those simulations partly measures our model
rather than the world. That objection is live and is queued for Fable.

**But it bites much less for this use than for calibration.** A calibration claim is *absolute* — "when
we say 33%, it happens a third of the time" — so model error passes straight through. A recommendation
is *relative*: both branches of "Bowers or Olave" are simulated under the **same** opponent model, so
the shared error largely cancels in the comparison. Getting the ordering right is far more robust to a
mis-specified opponent model than getting the probability right.

Specify how much cancels rather than asserting that it does. A sensitivity analysis over plausible
`lambda` values — does the recommended ordering flip? — is the honest form of that answer, and it is
cheap because it is simulation, not data collection.

## What to specify

1. **The evaluation metric.** Expected roster value at what horizon — next pick, next two, end of
   draft? Each is a different claim and a different cost.
2. **Simulation count and stopping rule**, with the Monte Carlo standard error stated. This is where
   false precision creeps in: 10,000 sims give a tight interval around *our model's* answer, not
   around the truth. Report both, and never present the former as the latter.
3. **Lambda sensitivity.** Sweep plausible values; report whether the ordering is stable. If the
   recommendation flips within the range of `lambda`'s own uncertainty (SE 0.070), say so plainly —
   that would mean the lookahead is not decision-relevant yet, which is a finding, not a failure.
4. **Cost and latency.** This runs mid-draft under a pick clock. If a full simulation cannot return in
   time, specify the degraded mode and what it loses.
5. **What it must never claim.** The output is "under our opponent model, this ordering held in N% of
   simulations" — not "this is the better pick." The distinction is the whole product.

## Pre-committed rule

Before running anything: state the threshold at which lookahead replaces plain VBD in the
recommendation, and the threshold at which it is judged not decision-relevant and shelved. Write both
down first. Adopting it because the output looks sophisticated is exactly the failure mode
pre-registration exists to prevent.

## Done looks like

An ADR draft with the metric, the simulation design, the sensitivity analysis, the honest statement of
what simulation-derived intervals do and do not measure, and both pre-committed thresholds. Then
`backend` reviews for feasibility and latency. Build only after that.
