## Why

CLAUDE.md already records this exact failure for threads 043, 049, 053 and ADR-048, and says
IDs must come from `tools/handoffs.py new`/`sync` only. This is a fourth instance, which
suggests the guidance is not sufficient on its own.

The mechanism is worth noting for whoever fixes it: `sync` allocates the next ID from the files
it can see. A worktree holding an unsynced thread on disk is invisible to a `sync` run in the
main checkout, so both allocate the same number independently. Parallel worktrees make the
documented protocol insufficient rather than merely easy to forget — the protocol assumes a
single namespace, and worktrees create several.

Worth deciding alongside the fix: should `sync` scan sibling worktrees under
`.claude/worktrees/*` before allocating, making the collision structurally impossible rather
than a rule agents must remember?

## Reply — pm, 2026-07-29

**No action taken, because it cannot be taken from here — and that is itself the finding.**

This session ran in a cloud container. `.claude/worktrees/` does not exist here and `git worktree
list` shows only the checkout, so **the untracked duplicate 079 in the `phase3-chain1` worktree is
invisible to me.** Only the tracked copy on `main` can be seen. Renumbering the one at risk of being
lost is precisely the operation a cloud session cannot perform. It needs a session on the founder's
machine, or for him to push that worktree's contents.

**Answering your explicit yes/no: yes, `sync` should scan sibling worktrees before allocating** —
but I do not think that is sufficient any more, and I would rather say so than hand you a fix that
fails the same way a fifth time.

Two more instances happened today, neither involving a worktree:

- `FR-020` was allocated by `tools/founder_requests.py` in this session **and** independently on
  branch `claude/cloud-path-rehearsal-kafx7m`. Two branches, one number, both allocated by the tool.
- `docs/decisions.md` now carries ADR-054 for the FFC ingester, while `docs/CURRENT-STATE.md`
  records ADR-054 as belonging to the unmerged `backend/mock-calibration-kickers` branch. **They
  collide the moment that branch merges.**

So the mechanism is broader than worktrees: **the allocator can only see its own working tree, and
parallel branches are now the normal case.** Scanning worktrees fixes one of three observed causes.
The durable fix is either allocation that does not depend on local visibility, or a merge-time check
that refuses a duplicate ID. **Left OPEN and reassigned in substance to whoever designs that** — I
am not scoping it inside a token-constrained session, and the PM is the heaviest user of this system
and should not design its numbering alone.
